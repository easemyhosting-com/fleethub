# Local self-onboarding

For a new installation, choose the built-in encrypted store or connect an Infisical you already operate. Install a new Infisical with its upstream guide. The bundled Infisical profile is deprecated and retained for existing installations. Local CLIProxyAPI remains an explicit option. The [current plan](60-reuse-first-onboarding-and-ux-plan.md) specifies independent connections. The explicit legacy `integrations` profile still starts both for compatibility. These steps affect only the local Docker host you choose. FleetHub does not install Tailscale, modify your cloud servers, or access the Docker socket.

## Connect existing services (recommended)

1. Start FleetHub with its own PostgreSQL database and a private environment file. Set `FLEETHUB_AUTH_SECRET` and `FLEETHUB_BOOTSTRAP_TOKEN` to separate random values of at least 32 bytes. Set `FLEETHUB_DB_PASSWORD` for a new database. If a FleetHub database already exists, retain its original password and volume rather than regenerating credentials.
2. Set `FLEETHUB_APP_URL` to the browser origin. Open FleetHub and register the first operator with the bootstrap token. After registration, remove `FLEETHUB_BOOTSTRAP_TOKEN` from the running environment when practical. Existing operators cannot be replaced with that token.
3. Use either the built-in encrypted store, which needs no external service, or Infisical. For an existing Infisical, set `INFISICAL_URL` to the URL reachable **from FleetHub's container** and allowlist its exact origin in `FLEETHUB_ONBOARDING_ALLOWED_ORIGINS`, then create a project and a Universal Auth machine identity with only the needed project/environment permissions. Enter its client ID and secret as `INFISICAL_UNIVERSAL_AUTH_CLIENT_ID` and `INFISICAL_UNIVERSAL_AUTH_CLIENT_SECRET`; restart FleetHub to apply them. Do not use an Infisical account password in these fields.
4. For an existing CLIProxyAPI, set `CLIPROXY_API_KEY` and `CLIPROXY_MANAGEMENT_KEY` to its distinct inference and management keys, and allowlist its exact origin in `FLEETHUB_ONBOARDING_ALLOWED_ORIGINS`. Its management console is generally at `<base URL>/management.html`, on the same API port. A working model request with an inference key does not validate management access. Keep its OAuth credential directory and configuration backed up.
5. If you choose Tailscale, install and enroll the host using Tailscale's own instructions. Tailscale verification is optional and does not gate credentialed provider onboarding. Configure an API key with Basic authentication, or a scoped read-only OAuth access token with `TAILSCALE_API_AUTH=bearer`, and set `TAILSCALE_API_TOKEN` and the enrolled `TAILSCALE_DEVICE_ID`; enrolling a host is a separate action. Avoid placing a tailnet API token in CLIProxy or Infisical configuration.

## Guided fresh local services

1. Install Docker with Compose and Node.js 24.22.1. Ensure local ports 3060, 8088, 8317, and 8085 are free. No local containers are started by the helper.
2. In the repository root, select your new setup directory with `export FLEETHUB_SETUP_DIR="$PWD/.local-setup"`, then run `node scripts/prepare-local-setup.mjs --directory "$FLEETHUB_SETUP_DIR"`. Set `FLEETHUB_SETUP_DIR` to your chosen absolute private path instead when using a custom location. Keep this variable set for the commands below. It creates `.local-setup/.env`, `.local-setup/cliproxy-config.yaml`, and `.local-setup/tailscale-status.json`, with private permissions on the two secret-bearing files. The status file is readable by FleetHub's unprivileged container user and is mounted read-only. An existing setup directory or `.env` is never overwritten. An existing installation must keep its original setup directory; do not rerun the helper there. Preserve these files; losing the Infisical encryption key can make stored secrets unreadable.
3. Review `CLIPROXY_IMAGE` and `INFISICAL_IMAGE` in the generated env file. Defaults are pinned to immutable image digests resolved from Docker Hub on 2026-10-26. Review and deliberately update these digests when upgrading; the containers are not automatically updated. Never commit the generated files.
4. Start FleetHub alone with `docker compose --env-file "$FLEETHUB_SETUP_DIR/.env" up -d --build fleetdeck inventory-worker`. Optional local stacks start only when you explicitly choose them:
   - Infisical: connect an existing server, or install a new server with the [upstream guide](https://infisical.com/docs/self-hosting/deployment-options/docker-compose). For an **existing bundled installation only**, validate with `docker compose --env-file "$FLEETHUB_SETUP_DIR/.env" --profile infisical config --quiet`, then run `docker compose --env-file "$FLEETHUB_SETUP_DIR/.env" --profile infisical up -d infisical`. Its PostgreSQL and Redis start as dependencies and publish no host ports.
   - CLIProxyAPI: validate with `docker compose --env-file "$FLEETHUB_SETUP_DIR/.env" --profile cliproxy config --quiet`, then run `docker compose --env-file "$FLEETHUB_SETUP_DIR/.env" --profile cliproxy up -d --build cli-proxy-api`.
   - Keep your existing Compose project name and private env-file path when extending an installation, so Docker reuses the original named volumes. The legacy `--profile integrations` remains an explicit combined compatibility option; it is not a default or fallback.
5. Open FleetHub at `http://localhost:3060` and create the first operator with `FLEETHUB_BOOTSTRAP_TOKEN` from the private env file. Choose the built-in store or connect your Infisical. For Infisical, open its console and create a dedicated fleethub project with an /accounts folder and a scoped Universal Auth machine identity. Put that identity's client ID and secret into the private runtime configuration. Existing bundled installations retain their console at `http://localhost:8088`.
6. If you selected local CLIProxyAPI, open its bundled Management Center at `http://localhost:8317/management.html`. Use the `management.secret-key` in the private CLIProxy configuration to sign in. The `access.api-keys` entry is for inference clients and has different permissions. OAuth logins and provider setup take place in CLIProxyAPI's supported UI or CLI. Its auth, logs, and plugin data use persistent Docker volumes.
7. Optionally, install and enroll this host in Tailscale separately. Add a scoped `TAILSCALE_API_TOKEN` and the enrolled `TAILSCALE_DEVICE_ID` to the private env file for the Tailscale verification step, then recreate FleetHub. Before using Verify, refresh the host status file with `tailscale status --json > "$FLEETHUB_SETUP_DIR/tailscale-status.json"` on the Docker host. FleetHub reads this file without write access and requires a recent running host status whose self device ID matches the device returned by the Tailscale API. Alternatively, it can match the authorized device address to an actual local network interface. Refreshing this file does not enroll the host.

Docker's `--env-file` supplies Compose substitutions; it is not an encrypted store. Secure backups of the env file, CLIProxy config, Infisical database volume, and CLIProxy auth volume are your responsibility. The Infisical machine identity remains a manual step because the first account and project must exist before one can be scoped. Local loopback port publishing keeps these services off the LAN by default; remote access requires a separately secured route.

CLIProxyAPI references: [v8 configuration options](https://help.router-for.me/configuration/options), [Management Center](https://help.router-for.me/management/webui), [Docker Compose guide](https://help.router-for.me/docker/docker-compose). Infisical reference: [self-hosting with Docker Compose](https://infisical.com/videos/self-host-infisical).

## Verify and resume setup

Open **Setup connections**. Choose and verify either Infisical or the built-in encrypted store. Private access and CLIProxy are independent optional connections. Public settings persist across restarts. Verification expires after 15 minutes by default, with a configurable duration. Changes invalidate the affected connection, not unrelated steps. Stale secret-store checks are retried on demand before credentialed registration. See [implemented setup tiers](45-setup-tiers-and-builtin-secret-store.md).

Enter the Infisical API address reachable from FleetHub separately from its browser console address. Select an existing project, environment, and folder. Verification creates a uniquely named temporary secret in that exact scope, reads it back, and deletes it. Grant the machine identity only the necessary create/read/delete permissions there. An API identity is a bootstrap credential and remains outside the vault it unlocks, in protected runtime configuration.

CLIProxy verification calls `/v1/models` with the inference key and `/v8/management/credentials` with the management key. The console URL is configured separately and is not inferred by changing ports. Open that link in your browser to confirm the console route is reachable from your own device. Verification checks API capabilities, not live upstream quotas. Once gateway settings are saved, **Check capabilities** on the CLIProxy step reads the same two endpoints on request and shows whether each key is accepted, the listed model count, upstream accounts by provider with disabled or reported-unavailable counts, and that quota is not measured. It changes nothing and is not run automatically.

Provider registration offers inventory-only mode before setup is ready. Once one secret backend verifies, you may save credentials to that backend. Cloudflare zones, Upstash Redis databases, Supabase projects, Neon projects and OCI inventory can be collected by the separate inventory worker. New accounts stay pending until a complete scan succeeds; unsupported providers remain manual. From an inventory-only account, use **Connect credentials** to attach management credentials after setup without duplicating the account. See the inventory guide. A stored credential is not proof of a working cloud account, and it does not grant task-placement permission. OCI collection remains read-only; it does not enable workload execution.

If a scan returns no resources for a scope that previously had inventory, FleetHub retains the previous snapshot and reports `unexpected_empty`. After verifying in the provider console that the scope is empty, an operator can send `{"accountId":"<account-id>","confirmEmpty":true}` to `POST /api/inventory/refresh`. This queues one fresh scan. Only a successful scan can mark covered resources missing. If that scan fails, FleetHub retains the previous snapshot and consumes the confirmation.

The configured Tailscale API authentication defaults to Basic for API keys. For a scoped OAuth access token, set `TAILSCALE_API_AUTH=bearer`; refresh expiring tokens in the protected runtime environment and reverify. A credential change invalidates that connection's verification.

Private API origins must be explicitly allowlisted before FleetHub sends credentials. The host status snapshot is trusted bootstrap evidence and must remain controlled by the operator. A snapshot never enrolls a host or changes tailnet permissions.

## Reuse-first setup controls

Infisical and CLIProxy each open in **Connect existing** mode. **Set up locally** reveals only that service's startup command and never executes it. **Use local Compose addresses** fills the API and console addresses for a FleetHub container in the same Compose project; it does not save or start anything. For FleetHub running directly on the host, use the host-reachable addresses instead. New API and console URLs must be entered explicitly. New empty Infisical environment/path fields default to `dev` and `/accounts`; create that folder first. Saved scopes are retained.

An already verified backend reopens directly. Changing service resets the local-install view. **Skip for now** on private access or gateway persists a separate skipped flag without changing its saved settings or revoking existing access. Reopening setup displays the flag. Saving settings or successfully verifying clears it. Skipping never verifies a connection or grants credential-storage readiness. Unsaved changes must be saved or explicitly discarded before moving between connections. Discard restores the saved settings without sending a write request. A verified secret backend enables provider registration independently of optional connections.

## Bundled Infisical deprecation

New deployments should use FleetHub's built-in store, connect an existing Infisical, or follow the [upstream self-hosting guide](https://infisical.com/docs/self-hosting/deployment-options/docker-compose). FleetHub retains the `infisical` and legacy `integrations` Compose profiles for compatibility. No removal date is set, and this release does not change service names, volume names or existing data.

Before moving an existing installation, back up both databases, the private configuration and encryption keys. Verify restoration in isolation, confirm the destination project's scoped machine identity from both web and worker, and migrate each credential with readback and rollback evidence. Changing the configured vault URL is not a migration. Folder changes within the same verified origin, project and environment retain access to older references; moving origins requires explicit migration.

Keep the original services and volumes until the destination is verified. Stopping a service preserves its volumes. Never run `docker compose down --volumes` as a migration step. The built-in backend does not automatically import existing Infisical credentials.

## Colima and bind mounts

The Compose file bind-mounts the CLIProxy config and the Tailscale status file. Colima only shares the host directories listed under `mounts:` in its configuration; an unshared path makes Docker create an empty directory in its place, and CLIProxy then restarts with `config.yaml: is a directory`. Create the setup directory (`node scripts/prepare-local-setup.mjs --directory <path>`) inside a path Colima shares, or add that path to Colima's mounts.


Service credentials require HTTPS outside loopback. Loopback HTTP is supported for local simulators. For an isolated, trusted container network, explicitly set `FLEETHUB_ALLOW_INSECURE_SERVICE_HTTP=true` in the FleetHub runtime environment. This permits cleartext credentials on that network, so keep it disabled for remote services. The exact-origin onboarding allowlist still applies, and credential-bearing requests reject redirects.
